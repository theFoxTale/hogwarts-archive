# React: Модульное тестирование

## 🧠 Описание задачи

В этой задаче ваша цель — написать комплексные модульные тесты для компонентов-классов, созданных во время **Недели 1 - Компоненты-классы**. Основное внимание здесь уделяется тестированию, поэтому рекомендуется избегать изменения или рефакторинга компонентов на этой неделе. **Обратите внимание**: вам **не разрешается преобразовывать компоненты** в функциональные на данном этапе.

Вы должны использовать **Jest** или **Vitest** в качестве тестового исполнителя и **React Testing Library (RTL)** для тестирования компонентов, чтобы покрыть ключевое поведение, логику рендеринга и взаимодействия с пользователем.

## ⚠️ ВАЖНОЕ УВЕДОМЛЕНИЕ

🚨 Тесты, которые вы напишете в этом задании, ДОЛЖНЫ продолжать работать после рефакторинга компонентов в функциональные компоненты на следующей неделе. Сосредоточьтесь на тестировании **поведения и публичного API**, а не на деталях реализации, таких как внутреннее состояние или методы жизненного цикла!

## 🎯 Цели задания

- Получить опыт написания модульных тестов для React компонентов-классов
- Понять, как тестировать поведение компонентов, пропсы, события и условный рендеринг
- Научиться имитировать (мокать) API-вызовы и внешние зависимости
- Практиковаться в тестировании пользовательских взаимодействий и изменений состояния компонентов
- Подготовить надежную основу для тестов для будущего рефакторинга (**Неделя 3 - Функциональная маршрутизация**)

## Функциональные требования (максимум **100 баллов**)

### Функция 1: Покрытие тестами (**14 баллов**)

**Как** разработчик
**Я хочу** обеспечить высокое покрытие тестами
**Чтобы** мои компоненты были надежно протестированы

**Сценарий:** Достижение минимального покрытия

- **При условии**, что я написал тесты для всех компонентов
- **Тогда** покрытие операторов (statement) составляет не менее 80%
- **И** покрытие ветвей (branch), функций (function) и строк (line) составляет не менее 50%

**Критерии приемки:**

- Набор тестов достигает не менее 80% покрытия операторов.
- Покрытие ветвей, функций и строк составляет не менее 50% каждое.
- Покрытие измеряется и отображается с помощью инструментов покрытия Jest или Vitest.

### Функция 2: Отсутствие функциональных изменений (**14 баллов**)

**Как** разработчик
**Я хочу** тестировать компоненты-классы без изменения их логики
**Чтобы** сохранить исходное поведение

**Сценарий:** Только написание тестов

- **При условии** существующих компонентов-классов
- **Когда** я пишу тесты
- **Тогда** я не изменяю реализацию компонентов

**Критерии приемки:**

- Во время тестирования не вносятся существенные изменения в логику или структуру компонентов-классов.
- Преобразование в функциональные компоненты не выполняется.
- Разрешены только изменения, улучшающие тестируемость, без изменения поведения.
- Логика и вывод компонентов должны оставаться практически неизменными.

### Функция 3: Тестирование, ориентированное на поведение (**14 баллов**)

**Как** разработчик
**Я хочу** тестировать поведение компонентов и публичный API
**Чтобы** тесты оставались действительными после рефакторинга

**Сценарий:** Фокус на поведении

- **При условии** наличия компонента
- **Когда** я пишу тесты
- **Тогда** я тестирую то, что компонент делает, а не то, как он это делает

**Критерии приемки:**

- Тесты сосредоточены на видимом пользователю поведении и выводе компонентов, а не на внутренних деталях реализации.

### Функция 4: Мокание API (**14 баллов**)

**Как** разработчик
**Я хочу** имитировать все внешние API-вызовы
**Чтобы** тесты были изолированными и быстрыми

**Сценарий:** Мокание API

- **При условии**, что компонент вызывает API
- **Когда** я запускаю тесты
- **Тогда** все API-вызовы имитируются

**Критерии приемки:**

- Все внешние API-вызовы имитируются с помощью Jest, Vitest или MSW.
- Во время выполнения тестов не выполняется реальных сетевых запросов.
- Тесты покрывают как успешные, так и ошибочные ответы API с помощью моков.

### Функция 5: Обработка ошибок (**14 баллов**)

**Как** разработчик
**Я хочу** тестировать сценарии с ошибками
**Чтобы** мои компоненты корректно обрабатывали ошибки

**Сценарий:** Тестирование ошибок

- **При условии**, что компонент может завершиться ошибкой
- **Когда** возникает ошибка
- **Тогда** сценарий с ошибкой тестируется

**Критерии приемки:**

- Тесты имитируют условия ошибок (например, неудачные API-вызовы, выброшенные ошибки в компонентах).
- Границы ошибок (error boundaries) тестируются на предмет того, что они перехватывают и обрабатывают ошибки должным образом.

### Функция 6: Пользовательские взаимодействия (**14 баллов**)

**Как** разработчик
**Я хочу** тестировать все пользовательские взаимодействия
**Чтобы** мои компоненты правильно реагировали

**Сценарий:** Тестирование взаимодействий

- **При условии** компонента с пользовательским вводом
- **Когда** пользователь взаимодействует (клики, отправка формы, изменения ввода)
- **Тогда** взаимодействие тестируется

**Критерии приемки:**

- Все пользовательские взаимодействия (клики, изменения ввода, отправка форм и т.д.) покрыты тестами.
- Тесты проверяют, что компоненты правильно реагируют на действия пользователя (например, обновление состояния, вызов колбэков, изменения рендеринга).
- Граничные случаи и недопустимые вводы тестируются для обеспечения надежной обработки пользовательских взаимодействий.

### Функция 7: Тестирование функциональности localStorage (**16 баллов**)

**Как** разработчик
**Я хочу** тестировать интеграцию с localStorage в компонентах
**Чтобы** поисковые запросы и соответствующие данные сохранялись должным образом

**Сценарий:** Тестирование поведения localStorage

- **При условии**, что компонент использует localStorage
- **Когда** компонент загружается или пользователь взаимодействует
- **Тогда** ожидается чтение из localStorage и запись в него

**Критерии приемки:**

- Тесты проверяют, что компонент считывает правильное значение из localStorage при монтировании.
- Тесты проверяют, что компонент записывает правильное значение в localStorage после действий пользователя (например, поиска).
- Тесты покрывают случаи, когда localStorage пуст, содержит значение или обновляется.
- Тесты гарантируют, что интеграция с localStorage не нарушает поведение компонента.

## Технические требования

1. **Управление ветками**: Создайте отдельную ветку от "class-components". Название ветки: **"unit-testing"**

2. **Настройка тестового исполнителя**:
   - Настройте **Jest** или **Vitest** с React Testing Library
   - Настройте отчетность о покрытии тестами со следующими минимальными порогами:

   ```json
   {
     "coverageThreshold": {
       "global": {
         "statements": 80,
         "branches": 50,
         "functions": 50,
         "lines": 50
       }
     }
   }
   ```

3. **Настройка покрытия**:
   - Пример настройки покрытия:

   ```typescript
   coverage: {
     include: ['src/**/*.{js,jsx,ts,tsx}'],
     exclude: [
       'src/**/*.test.{js,jsx,ts,tsx}',
       'src/**/*.spec.{js,jsx,ts,tsx}',
       'src/index.{js,jsx,ts,tsx}',
       'src/setupTests.{js,ts}',
       'src/**/*.d.ts'
     ]
   }
   ```

4. **Обязательные файлы тестов**:
   - Создайте файлы `.test.tsx` или `.spec.tsx` для каждого компонента
   - Настройте вспомогательные утилиты и моки в отдельной директории `__tests__` или `test-utils`

## Предлагаемые сценарии тестирования

⚠️ Вы можете использовать следующие сценарии в качестве руководства при написании тестов. Не стесняйтесь добавлять больше тестов в зависимости от конкретного поведения и требований ваших компонентов. Ваше приложение может отличаться от этих примеров, поэтому данные сценарии являются **только предложениями**. Стремитесь к **80% покрытия операторов тестами** как к целевому ориентиру.

### 1. Тесты компонента поиска (Search)

- **Тесты рендеринга**:
  - Рендерит поле ввода поиска и кнопку поиска
  - При монтировании отображает ранее сохраненный поисковый запрос из localStorage
  - Показывает пустое поле ввода, если сохраненного запроса нет
- **Тесты пользовательских взаимодействий**:
  - Обновляет значение ввода, когда пользователь печатает
  - Сохраняет поисковый запрос в localStorage при нажатии кнопки поиска
  - Обрезает пробелы в поисковом запросе перед сохранением
  - Запускает колбэк поиска с правильными параметрами
- **Интеграция с localStorage**:
  - Извлекает сохраненный поисковый запрос при монтировании компонента
  - Перезаписывает существующее значение в localStorage при выполнении нового поиска

### 2. Тесты компонента результатов / списка карточек (Results/CardList)

- **Тесты рендеринга**:
  - Отображает правильное количество элементов, когда данные предоставлены
  - Отображает сообщение "нет результатов", когда массив данных пуст
  - Показывает состояние загрузки во время получения данных
- **Тесты отображения данных**:
  - Корректно отображает названия и описания элементов
  - Корректно обрабатывает отсутствующие или неопределенные данные
- **Тесты обработки ошибок**:
  - Отображает сообщение об ошибке, когда вызов API завершается неудачей
  - Показывает соответствующую ошибку для различных HTTP статусов (4xx, 5xx)

### 3. Тесты компонента карточки / элемента (Card/Item)

- **Тесты рендеринга**:
  - Корректно отображает название и описание элемента
  - Корректно обрабатывает отсутствующие пропсы

### 4. Тесты компонента загрузки (Loading)

- **Тесты рендеринга**:
  - Рендерит индикатор загрузки (спиннер, скелетон и т.д.)
  - Показывается/скрывается в зависимости от пропса `loading`
- **Тесты доступности**:
  - Имеет соответствующие ARIA-метки для скринридеров, если ваш индикатор загрузки имеет `aria-label`

### 5. Тесты границы ошибок (Error Boundary)

- **Тесты перехвата ошибок**:
  - Перехватывает и обрабатывает ошибки JavaScript в дочерних компонентах
  - Отображает резервный интерфейс (fallback UI) при возникновении ошибки
  - Логирует ошибку в консоль
- **Тесты кнопки ошибки**:
  - Выбрасывает ошибку при клике на тестовую кнопку
  - Активирует резервный интерфейс границы ошибок

### 6. Тесты основного компонента приложения (App)

- **Интеграционные тесты**:
  - Выполняет начальный API-вызов при монтировании компонента
  - Обрабатывает поисковый запрос из localStorage при начальной загрузке
  - Управляет состояниями загрузки во время API-вызовов
- **Тесты интеграции API**:
  - Вызывает API с правильными параметрами
  - Обрабатывает успешные ответы API
  - Обрабатывает ошибочные ответы API
- **Тесты управления состоянием**:
  - Обновляет состояние компонента на основе ответов API
  - Правильно управляет состоянием поискового запроса

### 7. Тесты интеграции API

- **Имитированные (моканные) API-вызовы**:
  - Используйте `jest.mock`, `vi.mock` или `MSW` для имитации API-вызовов
    - [Jest Mock Functions](https://jestjs.io/docs/mock-functions)
    - [Vitest Mocking](https://vitest.dev/guide/mocking)
    - [Mock Service Worker](https://mswjs.io/docs)
  - Тестируйте как успешные, так и ошибочные сценарии

### 8. Настройка (Setup)

- Наконец, обновите Husky для запуска тестов в pre-push хуке, гарантируя, что тесты автоматически выполняются перед отправкой кода.

### 9. Требования к сдаче (Submission Requirements)

1. Все тесты должны проходить: `npm run test`
2. Отчет о покрытии должен показывать ≥50% по всем метрикам и ≥80% по операторам: `npm run test:coverage`
3. Отсутствие ошибок или предупреждений в консоли во время выполнения тестов
4. Тесты должны быть детерминированными (никаких «flaky» тестов)
5. Все внешние зависимости должны быть правильно имитированы

## 📚 Часто задаваемые вопросы (FAQ)

### ❓ Разрешено ли мне изменять существующие компоненты, чтобы упростить тестирование?

Да, при необходимости вам разрешается изменять код компонентов для улучшения тестируемости. Просто убедитесь, что вы не меняете логику и не преобразуете компоненты-классы в функциональные.

### ❓ Могу ли я добавлять атрибуты data-testid?

Да. Вы можете добавлять атрибуты `data-testid` при необходимости, но предпочтение следует отдавать семантическим запросам, таким как `getByRole`, `getByLabelText` или `getByText`, следуя приоритету запросов Testing Library.

### ❓ Могу ли я использовать реальные API-вызовы в тестах?

Нет. Вы должны тестировать свой код, а не бэкенд. Все API-вызовы должны быть имитированы с помощью `jest.mock`, `vi.mock` или таких инструментов, как Mock Service Worker (MSW). Тесты не должны полагаться на внешние сервисы.

### ❓ Если один файл имеет низкое покрытие, но общее покрытие по проекту в порядке, потеряю ли я баллы?

Нет. Правило применяется только к общему (глобальному) покрытию.

### ❓ Как настроить пороговые значения покрытия?

В вашем конфигурационном файле тестов (например, `jest.config.js`):

```typescript
coverageThreshold: {
    global: {
        statements: 80,
        branches: 50,
        functions: 50,
        lines: 50,
    },
},
```

### ❓ Следует ли мне тестировать main.tsx или App.tsx?

Вам не нужно тестировать main.tsx напрямую. Сосредоточьтесь на таких компонентах, как App.tsx, и на всем, что рендерится внутри него.

### ❓ Требуется ли развертывание для этого задания?

Нет, развертывание не является обязательным для задания по модульному тестированию.
Тем не менее, развертывание вашего приложения (например, на GitHub Pages, Vercel или Netlify) настоятельно рекомендуется — это упрощает процесс проверки и демонстрирует хорошие практики разработки.
Если вы хотите развернуть приложение, не стесняйтесь, но это не повлияет на вашу оценку.
