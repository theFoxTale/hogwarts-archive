# Выполнение API-запросов в React

Это задание является продолжением задачи по управлению состоянием. В рамках этого задания вы реализуете надлежащую загрузку данных и механизмы кэширования, используя современные библиотеки для выполнения запросов.

## Функциональные требования (максимум **100 баллов**)

### Функция 1: Интеграция API (**25 баллов**)

**Как** разработчик
**Я хочу** использовать современную библиотеку для выполнения API-запросов
**Чтобы** моя загрузка данных была эффективной и поддерживаемой

**Сценарий:** Настройка библиотеки запросов

- **Дано** я выбрал решение для управления состоянием (Redux или Zustand)
- **Когда** я настраиваю выполнение API-запросов
- **Тогда** я использую RTK Query (для Redux) или TanStack Query (для Zustand) для всех API-вызовов

**Критерии приёмки:**

- RTK Query или TanStack Query интегрированы и настроены. [10 баллов]
- Все API-вызовы выполняются с использованием выбранной библиотеки запросов. [5 баллов]
- Реализованы правильные стратегии инвалидации кэша. [5 баллов]
- Время жизни кэша (TTL) настраивается через переменную окружения. [5 баллов]

### Функция 2: Кэширование данных и состояния загрузки (**25 баллов**)

**Я хочу** видеть индикаторы загрузки и чтобы данные кэшировались
**Чтобы** навигация была быстрой, и я знал, когда данные загружаются

**Сценарий:** Кэширование данных и загрузка

- **Дано** я перемещаюсь между страницами или открываю детали элемента
- **Когда** данные загружаются
- **Тогда** отображается индикатор загрузки
- **И** ранее загруженные данные кэшируются и повторно используются, когда это возможно

**Критерии приёмки:**

- Индикаторы загрузки показываются во время получения данных. [13 баллов]
- Данные кэшируются и повторно используются при навигации. [12 баллов]

**Как** пользователь
**Я хочу** видеть понятные сообщения об ошибках, когда API-вызовы не удаются
**Чтобы** я понимал, что пошло не так

**Сценарий:** Отображение состояния ошибки

- **Дано** вызов API завершается ошибкой
- **Когда** я использую приложение
- **Тогда** отображается понятное, читаемое человеком сообщение об ошибке

**Критерии приёмки:**

### Функция 4: Ручная инвалидация кэша (**10 баллов**)

**Чтобы** я мог убедиться, что у меня самая актуальная информация

- **Дано** я просматриваю список или детали

- Реализована специальная кнопка обновления. При нажатии она явно инвалидирует кэш соответствующих данных и запускает повторную выборку. [10 баллов]

### Функция 5: Покрытие тестами для функций запросов (**20 баллов**)

## Технические требования

1. Создайте отдельную ветку для этого задания от ветки с задачей по управлению состоянием. Название ветки: «api-queries»

2. Интеграция библиотеки:
   - Для пользователей Redux:
     - Реализуйте endpoints RTK Query для всех ваших API-вызовов
     - Используйте хуки RTK Query в ваших компонентах
     - Реализуйте правильные стратегии инвалидации кэша
   - Для пользователей Zustand:
     - Настройте TanStack Query с соответствующей конфигурацией
     - Создайте пользовательские хуки для ваших запросов, используя TanStack Query
     - Реализуйте правильное управление кэшем

3. Управление данными:
   - Элементы, возвращённые для текущей страницы, должны быть правильно закэшированы
   - Детали выбранного в данный момент элемента должны быть закэшированы
   - Состояния загрузки должны отслеживаться и отображаться соответствующим образом
   - Состояния ошибок должны обрабатываться и отображаться пользователю

4. Обновление тестов:
   - Обновите ваши тесты, чтобы покрыть новую функциональность запросов
   - Протестируйте состояния загрузки, ошибок и поведение кэширования

## Часто задаваемые вопросы (FAQ)

### ❓ Что означает «Детали выбранного в данный момент элемента должны быть закэшированы»?

Это означает, что когда пользователь открывает детальный просмотр элемента, данные, полученные для этого элемента, должны быть закэшированы, чтобы повторное открытие позже не вызывало новый сетевой запрос.

### ❓ Сколько кнопок «Обновить» мне нужно?

Реализация зависит от вас:

- **Одна кнопка**, которая инвалидирует как данные списка, так и данные деталей, подойдёт.
- **Две кнопки** (одна в представлении списка, одна в представлении деталей) тоже подходят.
  Ключевое требование — продемонстрировать ручную инвалидацию кэша.

### ❓ В чём разница между инвалидацией кэша и повторной выборкой (refetch)?

- **Повторная выборка (Refetch)**: повторно запрашивает текущий запрос без очистки его ключа кэша.
- **Инвалидация (Invalidate)**: очищает кэш для запроса, так что следующий доступ вынуждает выполнить свежий API-вызов.

### ❓ Должен ли я очищать дисковый кэш браузера?

Нет. Это задание касается только кэша в памяти RTK Query или TanStack Query.
Вы **не должны** управлять или обходить собственный HTTP-кэш браузера.

### ❓ Как проверить, что «Инвалидация кэша и повторная выборка работают правильно»?

Пример:

1. Открыть страницу 1 → выполняется запрос.
2. Открыть страницу 2 → выполняется запрос.
3. Вернуться на страницу 1 → запроса нет (данные берутся из кэша).
4. Нажать «Обновить» → запрос выполняется снова для страницы 1.
5. Повторить для поисковых запросов и страниц деталей.

### ❓ Что, если моя пагинация серверная?

Это нормально — кэширование должно гарантировать, что возврат к ранее посещённой странице не вызывает новый запрос, если только вы не инвалидируете её вручную.

### ❓ Могу ли я выполнять несколько запросов параллельно для CSV-экспорта?

Да:

- В RTK Query — создать endpoint, который принимает массив и загружает элементы (возможно, используя `Promise.all` внутри).
- В TanStack Query — использовать `useQueries` для параллельной выборки.

### ❓ Нужно ли устанавливать `staleTime` или подобные опции?

Необязательно, но вы можете настроить их для контроля свежести данных. Основное требование — навигация между уже загруженными страницами не должна вызывать ненужные API-вызовы.

### ❓ Могу ли я использовать React Query Devtools или Redux Devtools?

Да. Они не считаются библиотеками пользовательского интерфейса и не повлекут штрафов.
