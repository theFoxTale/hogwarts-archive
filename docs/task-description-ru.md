# Настройка React-проекта. Классовые компоненты. Error Boundary

## Функциональные требования (максимум **100 баллов**)

### Функция 1: Структура макета приложения (**5 баллов**)

**Как** пользователь
**Я хочу** видеть четко организованный макет страницы
**Чтобы** легко взаимодействовать с поиском и просматривать результаты

**Сценарий:** Организация макета страницы

- **При условии** что я нахожусь на странице приложения
- **Тогда** я должен видеть две отдельные области:
  - Меньшая область поиска вверху
  - Большая область результатов внизу

**Критерии приемки:**

- Страница содержит ровно две основные области: область поиска и область результатов.
- Обе области визуально различимы и четко разделены с помощью макета или стилей (например, отступы, границы или фоновый цвет).

### Функция 2: Функциональность поиска с локальным хранилищем (**15 баллов**)

**Как** пользователь
**Я хочу** иметь интерфейс поиска, который запоминает мой последний поиск
**Чтобы** я мог продолжить предыдущую сессию поиска

**Сценарий:** Начальная загрузка компонента поиска

- **При условии** что я открываю приложение
- **Когда** компонент поиска загружается
- **Тогда** он должен проверить локальное хранилище на наличие предыдущего поискового запроса
- **И** заполнить поле ввода, если запрос существует
- **Или** оставить его пустым, если предыдущий запрос не найден

**Критерии приемки:**

- При загрузке приложения компонент поиска проверяет локальное хранилище на наличие ранее сохраненного поискового запроса:
  - Если сохраненный запрос существует, он автоматически отображается в поле ввода.
  - Если сохраненного запроса в локальном хранилище нет, поле ввода остается пустым.

### Функция 3: Отображение результатов поиска (**10 баллов**)

**Как** пользователь
**Я хочу** видеть результаты поиска четко отображенными
**Чтобы** легко просматривать найденные элементы

**Сценарий:** Формат отображения результатов

- **При условии** что я смотрю на область результатов
- **Тогда** каждый результат должен отображать:
  - Название элемента
  - Описание элемента

**Критерии приемки:**

- Результаты поиска отображаются в области результатов после выполнения поиска.
- Каждый элемент результата включает как минимум следующие поля:
  - Название
  - Описание
- Результаты представлены в четком и удобочитаемом формате (единообразные отступы, выравнивание и типографика).

### Функция 4: Начальная загрузка данных (**10 баллов**)

**Как** пользователь
**Я хочу** видеть релевантные элементы при первом открытии приложения
**Чтобы** я мог сразу начать просмотр

**Сценарий:** Загрузка данных по умолчанию

- **При условии** что я открываю приложение
- **Когда** оно загружается в первый раз
- **Тогда** оно должно получить первую страницу элементов на основе:
  - Поискового запроса из поля ввода, если он существует
  - Всех доступных элементов, если поискового запроса нет

**Критерии приемки:**

- При начальной загрузке приложение **отправляет запрос данных** в соответствии с определенной логикой:
  - Если в поле ввода есть поисковый запрос, запрос включает этот запрос.
  - Если поискового запроса нет, запрос получает все доступные элементы.
- Элементы, **возвращенные запросом**, **отображаются** в области результатов.
- Отображаемые элементы **соответствуют запросу**, использованному в запросе.

### Функция 5: Выполнение поиска (**20 баллов**)

**Как** пользователь
**Я хочу** искать конкретные элементы
**Чтобы** находить релевантное содержание

**Сценарий:** Выполнение поиска

- **При условии** что я нахожусь на странице поиска
- **Когда** я ввожу поисковый запрос
- **И** нажимаю кнопку "Поиск"
- **Тогда** система должна:
  - Удалить конечные пробелы из ввода
  - Получить первую страницу соответствующих результатов
  - Обновить отображение новыми результатами

**Критерии приемки:**

- При нажатии кнопки **Поиск**, если введенный текст не изменился, **новый запрос не выполняется**.
- **Лишние пробелы** в начале или конце поискового текста **удаляются**.
- Приложение отправляет **запрос только на первую страницу** результатов.
- **Поисковый запрос** включен в запрос.
- **Область результатов** показывает элементы из ответа сервера.

### Функция 6: Сохранение поискового запроса (**5 баллов**)

**Как** пользователь
**Я хочу** чтобы мои поисковые запросы сохранялись
**Чтобы** я мог продолжить поиск позже

**Сценарий:** Сохранение поискового запроса

- **При условии** что я выполняю поиск
- **Когда** я нажимаю кнопку "Поиск"
- **Тогда** поисковый запрос должен быть сохранен в локальное хранилище
- **И** перезаписать любой существующий сохраненный запрос

**Критерии приемки:**

- Если поисковый текст **не изменился**, ничего не происходит.
- Если текст **изменился**, **очищенное значение** (без лишних пробелов) **сохраняется в локальное хранилище**, заменяя предыдущее.

### Функция 7: Индикация состояния загрузки (**10 баллов**)

**Как** пользователь
**Я хочу** знать, когда приложение загружает данные
**Чтобы** понимать, когда ждать результаты

**Сценарий:** Состояние загрузки API-запроса

- **При условии** что я инициирую любой API-запрос
- **Тогда** я должен видеть индикатор загрузки (спиннер/скелет/полоса загрузки/размытие)
- **И** индикатор должен оставаться, пока данные загружаются

**Критерии приемки:**

- **Индикатор загрузки** (например, спиннер, скелет или полоса загрузки) появляется **пока данные загружаются**.
- Индикатор **остается видимым**, пока данные не будут полностью получены и отображены.
- После завершения загрузки **индикатор скрывается**.

### Функция 8: Обработка ошибок (**10 баллов**)

**Как** пользователь
**Я хочу** получать уведомление, когда что-то идет не так
**Чтобы** понимать, почему мой запрос не удался

**Сценарий:** Неудачный API-запрос

- **При условии** что я делаю поисковый запрос
- **Когда** сервер возвращает ошибку (4xx или 5xx)
- **Тогда** я должен увидеть понятное сообщение об ошибке

**Критерии приемки:**

- Пользователю показывается **четкое, читаемое сообщение об ошибке**, когда сервер возвращает ошибку (4xx или 5xx).
- **Консоль остается чистой** — нет неперехваченных ошибок или ненужных логов ошибок.

### Функция 9: Граница ошибки приложения (**15 баллов**)

**Как** пользователь
**Я хочу** чтобы приложение обрабатывало ошибки gracefully
**Чтобы** я все еще мог использовать приложение, даже если части его не работают

**Сценарий:** Реализация границы ошибки (Error Boundary)

- **При условии** что в приложении возникает ошибка
- **Тогда** ошибка должна быть залогирована в консоль
- **И** должен отображаться запасной интерфейс
- **И** должна быть тестовая кнопка для симуляции ошибок

**Критерии приемки:**

- Доступна **тестовая кнопка** для симуляции ошибки приложения.
- Нажатие тестовой кнопки **вызывает ошибку**, которая **логируется в консоли**.
- **Запасной интерфейс** отображается, когда происходит ошибка.

## Технические требования

1. Создайте отдельную ветку для этого задания. Название ветки: `class-components`.

2. Следуйте требованиям по настройке проекта, указанным [здесь](./project-setup.md)

3. Выберите RESTful API, который поддерживает поиск и пагинацию (пагинация может быть реализована через параметры _offset_ и _limit_). Например: <https://pokeapi.co/>, для фанатов Star Wars <https://swapi.dev/api>, для фанатов Star Trek <https://stapi.co/api-documentation> (спецификацию OpenApi можно посмотреть здесь <https://editor.swagger.io/?url=https://stapi.co/api/v1/rest/common/download/stapi.yaml>), или вы можете выбрать другой API, соответствующий требованиям.

4. Все логические части должны быть разделены на отдельные компоненты, такие как CardList, Card, Search, Header, Main и т.д.

5. **Используйте классовые компоненты для доступа к событиям жизненного цикла или состоянию. Использование хуков запрещено на этом этапе. Потерпите, это ненадолго.**

6. Вы можете использовать CSS-фреймворки (например, Tailwind CSS).
